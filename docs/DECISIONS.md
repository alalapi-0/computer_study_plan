# Decisions

本文件记录影响项目长期推进方式的架构决策。每条 ADR 都应区分“当前阶段决策”和“未来可能演进”，避免把长期方向误写成当前事实。

## ADR-0001: 当前阶段继续使用 JSON 作为状态存储

- 日期：2026-05-05
- 状态：Accepted
- 背景：当前项目已有 `progress.json` 作为状态单一事实源，并由 Web UI / `mark_done.sh` 写入、`progress_data.js` 镜像到页面。
- 决策：当前阶段继续使用 JSON / JSONL 作为任务状态、动作记录、任务反馈和本地存档的存储格式。
- 原因：JSON 易读、易版本管理，配合轻量本地服务即可支持当前单人学习工作流。
- 后果：短期内无需引入数据库；当事件日志和查询需求明显超过 JSON 能力时，再评估 SQLite 或后端服务。

## ADR-0002: 当前阶段保留静态 progress.html，不立即引入前端框架

- 日期：2026-05-05
- 状态：Accepted
- 背景：当前 `progress.html` + `progress_ui.js` 已承担学习工作区、内联教程、工程终端、记录弹窗、练习脚本运行、存档和复盘入口。
- 决策：当前阶段保留原生 HTML + JavaScript + 轻量本地服务的实现方式，不立即引入 React、Vue 或其他前端框架。
- 原因：项目首先需要统一数据模型和任务体系，过早引入框架会增加维护成本和学习门槛。
- 后果：继续控制前端复杂度；当原生页面难以承载更复杂的任务操作、历史记录查询和反馈展示时，再评估前端架构升级。

## ADR-0003: 当前阶段保留 mark_done.sh，不立即改成完整后端服务

- 日期：2026-05-05
- 状态：Accepted
- 背景：Web UI 已成为正式学习入口；`mark_done.sh` 仍提供任务标记、撤销、状态查看和生成 `progress_data.js` 的兼容闭环。
- 决策：当前阶段继续保留并兼容 `mark_done.sh`，复杂交互优先通过 `scripts/progress_server.py` 提供本地 API。
- 原因：shell + 内嵌 Python 的方式对本地学习足够轻量，也能保护 Round 00 现有可运行能力。
- 后果：脚本复杂度需要被控制；如果后续读写逻辑明显变复杂，再拆出 Python 脚本或 API 服务。

## ADR-0004: 默认直接推进 main

- 日期：2026-05-05
- 更新：2026-07-06
- 状态：Accepted（替代原“必须独立分支”规则）
- 背景：项目会长期由多轮小任务推进，需要保证每轮可验证、可提交、可回滚。
- 决策：默认直接在 `main` 上完成、验证、commit，并在 remote 存在时 push `main`。独立分支只在用户明确要求 PR 审查、需要实验性大改、或 `main` 推送失败时使用。
- 原因：本仓库是单人本地学习总控仓库，直接主线推进更符合当前协作节奏；PR 流程会制造额外文档和操作成本。
- 后果：每轮必须更重视本地验证、提交范围说明和最终汇报；push 失败、冲突或验证连续失败时立即停止。

## ADR-0005: 动作记录与反馈先保持本地 JSON/JSONL

- 日期：2026-05-05
- 状态：Accepted
- 更新：2026-07-06
- 背景：Web UI 已经具备“用户动作 -> 记录 -> 反馈”的本地闭环，覆盖当前注册的 Linux Round 与计划阅读入口。
- 决策：继续使用本地 JSON/JSONL 保存进度、动作日志、任务反馈和存档；暂不引入数据库或完整后端架构。

- 后果：短期不会做登录、云同步或多人系统；服务化/API 化只在静态文件和本地脚本无法支撑需求时启动。

## ADR-0012: 执行结果、学习记录与任务完成保持不同语义

- 日期：2026-08-13
- 状态：Accepted
- 背景：Figma D05/D06 以命令校验、XP、掌握度和尝试次数表达反馈，但当前项目只有受限终端返回、白名单脚本运行、手动备注完成与静态任务反馈，没有 Attempt、规则验收或奖励模型。
- 决策：终端命令返回 0 只表示该命令正常结束；练习脚本结果展示真实返回码与输出；只有现有完成 API 成功保存后才显示任务完成回执。回执只呈现已保存的备注、证据、时间和任务数，不推导 XP、Mastery、尝试次数或复习日期。
- 原因：让 Figma 的反馈层级服务真实学习闭环，同时避免把进程状态伪装成学习验收。
- 后果：未来引入 Attempt / 规则反馈时可以增加正式“校验通过”状态，但必须由新的真实证据与数据契约驱动；现有三类状态不得被视觉文案重新混合。

## ADR-0013: 学习者模块检查点与项目治理 Stage 分离

- 日期：2026-08-13
- 状态：Accepted
- 背景：旧成长页把项目交付 Stage 与学习任务进度放在同一层，阶段结算范围又会受先前路线浏览状态隐式影响；当前系统尚无能力验收、奖励或正式通关模型。
- 决策：学习者视图按现有真实任务组呈现六个显式“模块检查点”，项目治理 Stage 只保留在规划文档。检查点完成仅表示该组全部注册任务都有完成标记；动作证据单独来自 action log，二者都不等同能力验收、Mastery 或奖励。课程完成判断必须覆盖全部且仅覆盖已注册的 80 个任务；实时进度不可核对时，镜像只作为只读快照，不允许触发检查点结论。
- 原因：让 D09/D10/M09/M10 的成长与结算层级建立在当前可追溯事实之上，同时保留未来引入 Attempt、规则验收和正式通关模型的空间。
- 后果：检查点选择进入导航历史；完成最后一项或脚本真实改变任务组状态后，可以进入该组检查点。未来扩展课程时应由课程注册关系提供检查点范围，不得把项目路线图阶段重新暴露为学习成就。

## ADR-0014: 路线浏览与当前学习任务选择分离

- 日期：2026-08-13
- 状态：Accepted
- 背景：旧路线页同时承担课程地图、完整任务列表和任务执行入口；浏览某个 Round 会隐式改变学习工作区的当前任务，路线成为第二个 Learn，并使历史/深链状态难以解释。Figma D02/M02 表达空间课程地图，D03/M03 表达模块总览，而不是另一套任务执行工作台。
- 决策：路线只负责 5 个真实学习模块和 1 个课程导览的地图、进度与周/任务摘要；任务阅读、终端、运行和完成继续由 Learn 承担。只有用户点击模块内显式学习入口时才设置要进入的任务；单纯选择模块、返回地图或使用旧路线深链不得改变全局下一任务。
- 原因：保持“地图 → 模块概览 → 显式进入学习”的可预测关系，同时让设计层级建立在现有 80 个注册任务和真实完成标记上。
- 后果：保留 `round`、`activeRound`、旧 Round flag 与 `#rounds/#progress/#lanes` 兼容入口；进度不可核对时地图仍可浏览但不推断 0%，镜像可用于只读浏览但不能作检查点完成结论。未来课程模型统一后，地图节点应由课程注册关系生成，而不是重新耦合 Learn 内部状态。

## ADR-0015: 复习视图只陈述真实动作与任务级建议

- 日期：2026-08-13
- 状态：Accepted
- 背景：Figma D07/M07 使用“错题、到期复习、掌握度、尝试次数”等示例表达复习场景，但当前项目只有任务完成标记、ActionEvent 和每任务聚合反馈，没有 Attempt、间隔调度、题目正误或 Mastery 模型。旧界面又把任意 action event 包装成 `REVIEW DUE`，并隐藏运行失败、超时或 noop 结果。
- 决策：当前课程的复习候选只表示“已注册任务发生过真实 action event”，不表示到期、弱项或掌握程度。0 动作时提供进入真实当前任务的单一引导；有动作后才展示最近动作、记录队列、任务级当前建议和时间线，并显式呈现事件结果。静态 `not_started` 反馈不产生复习候选；未知或已退出当前课程范围的历史事件不计入课程指标。查看或导航保持只读，完成、撤销和运行仍只经既有显式写入口。
- 原因：让 D07/M07 的优先行动层级建立在当前可追溯数据之上，同时避免用设计示例伪造尚未实现的学习判断。
- 后果：可见文案不得称“到期复习”“错题”“弱项”或“动作级反馈”，除非未来的数据模型和规则能够支持这些结论；引入 Attempt、间隔复习或 Mastery 时，应重新评估候选规则与反馈关联，而不是在现有 action log 上叠加推断。

## ADR-0016: 命令手册以登记 Markdown 为只读内容真源

- 日期：2026-08-13
- 状态：Accepted
- 背景：Figma D08/M08 使用命令条目、解锁数量、收藏与 Mastery 示例表达知识检索，但当前仓库只有 4 份 Round 命令小抄和 1 份课程路径 Markdown，没有命令级实体、收藏、解锁或掌握度模型。
- 决策：手册只接受 5 个稳定文档 ID 到现有 Markdown 路径的固定登记映射，并在运行内存中生成章节与文本搜索索引；URL 只记录登记 ID 和章节 ID，不接受原始文件路径。阅读、搜索、深链和专注模式保持只读，不改变任务或学习记录。
- 原因：让 D08/M08 的来源、索引与详情层级服务现有真实内容，同时避免复制正文形成第二真源或把设计示例包装成学习事实。
- 后果：新增资料必须先成为明确的课程内容真源并进入登记；读取失败、超时、空内容和竞态须显示真实资源状态。除非未来引入相应数据模型与写入契约，手册不得展示或持久化解锁、收藏、Mastery、Attempt 或阅读即完成。

## ADR-0017: 全局当前任务与显式学习任务使用不同状态语义

- 日期：2026-08-14
- 状态：Accepted
- 背景：路线、复习和检查点可以显式打开任意注册任务，但旧实现只把该选择保存在页面内存中；刷新或 Back / Forward 会回到全局下一任务，已完成任务还会被自动丢弃。与此同时，首页的“当前任务”必须继续表示由真实进度推导的全局下一项，不能被先前浏览过的任务污染。
- 决策：全局当前任务只由已核对进度和课程注册顺序推导；显式任务只在 Learn 中由 `task=<registered-task-id>` 持有，URL 是历史恢复权威，`history.state.taskId` 仅作镜像。进入 Learn 必须校验任务注册关系并创建独立历史条目；离开 Learn 创建不含 `task` 的新条目。已完成但仍在课程注册表中的任务可以显式复查、查看记录或撤销；无效、重复或路径形态的 `task` 会被替换清除，不能进入文件、终端或 API 请求。
- 原因：让 Home → Route → Learn → Review → Growth 的任务身份可预测、可复制和可恢复，同时保留“课程真实当前项”与“用户正在复查的任务”之间的事实差异。
- 后果：Home 始终显示全局下一任务；Route、Review 与检查点的显式入口进入精确任务。刷新、Back / Forward 和旧 Learn 锚点会恢复同一注册任务；任务切换或离开 Learn 会废弃不再属于当前学习表面的 reader / terminal 异步结果，包括没有任务 ID 的旧终端入口。该决策不改变进度、ActionEvent、本地 API 或课程数据协议。

## ADR-0018: 动效服从有界直接操控与用户降级偏好

- 日期：2026-08-14
- 状态：Accepted
- 背景：Figma Motion / Codex Handoff 以静态参数和状态机定义悬停、按压、拖拽、回弹与减少动效；文件当前没有可直接复用的编码动画轨道。旧实现会叠加视差与拖拽位移、只在启动时读取减少动效偏好，并用延迟隐藏和全屏闪烁表达通用状态，可能造成越界位移、隐藏视图短暂可交互及非局部反馈。
- 决策：装饰空间块在直接操控期间暂停视差，净位移遵守 Desktop ±28px、触控 ±18px 的设计边界，释放或取消后回到基准位置；减少动效偏好在运行中生效，取消手势和装饰位移，只保留必要且不超过 160ms 的透明度或颜色反馈。视图可见性、无障碍语义与焦点原子切换；通用反馈不再触发全屏闪烁。终端执行以单请求忙碌态锁定输入和按钮，并保持可见键盘焦点。
- 原因：让 Motion 契约服务可理解的因果关系、输入安全和无障碍，而不是增加装饰运动或伪造设计文件中不存在的动画轨道。
- 后果：后续动效不得引入持续漂浮、缩放式按压或在减少动效模式保留非必要位移；新的反馈应优先附着于动作来源。其余跨屏连续关系和组件状态仍需在后续独立检查点验证，不因本决策被视为完成。

## ADR-0019: Home → Learn 使用可中断的共享任务导航事务

- 日期：2026-08-14
- 状态：Accepted
- 背景：Figma H04 以 0 / 90 / 220 / 360 / 520ms 静态场景表达“首页当前任务成为真实学习表面”的空间连续性，但 `get_motion_context` 没有返回编码关键帧。现有实现已能用注册任务 ID、URL 与原子 view 切换保持任务事实，却只有通用整页淡入；初始化窗口还可能进入没有任务 ID 的 Learn，同一次历史遍历也会同时触发 `popstate` 与 `hashchange`。
- 决策：首页卡片和主按钮先冻结并校验同一个课程注册任务，再把任务上下文、canonical URL、render、view 可见性和 `#learnHeading` 焦点作为一次导航事务提交。浏览器支持 View Transition API、来源确为首页任务入口且未请求减少动效时，`.home-task-card` 与 `#continueCard` 使用 520ms 共享材料关系；否则同步执行原子降级，不引入自制 clone/polyfill。重复激活同一事务不新建历史，新的导航、窗口变化或动态 reduced-motion 会安全跳过旧装饰转场；所有转场 Promise 都显式收口。首次进度未核对时入口不可用，`popstate` / `hashchange` 对同一次遍历只处理一次。
- 原因：把 H04 的空间关系落实为渐进增强，同时不牺牲任务身份、即时焦点、Back / Forward、减少动效与不支持浏览器的可用性；静态 storyboard 只约束关系和总时长，不被伪装成 Figma 已提供的可执行轨道。
- 后果：Home → Learn 的语义与历史在所有浏览器相同，视觉连续性只在能力与偏好允许时增强。移动导航启用范围内（≤920px）Learn 同步采用显式单面板和 44px 核心触控约定；`tests/ui/` 的只读 fixture 必须继续拒绝写请求，并验证原生增强、原子降级、loading、重入、history 和关键断点。Route / Review / 检查点到 Learn 的共享转场仍需按后续真实价值独立裁定。

## ADR-0020: 完成与撤销使用可恢复的本地写入事务

- 日期：2026-08-14
- 状态：Accepted
- 背景：Figma D05/D06/M05/M06 与 Codex Handoff 要求动作、校验和事件记录一致；旧 Web 完成/撤销没有请求身份、全局 pending、超时恢复或响应顺序保护，本地多线程服务与 CLI 还可能并发覆盖进度、镜像、事件和反馈。瞬时 toast 无法让用户判断失败后输入是否保留，晚响应也可能重新打开旧回执。
- 决策：Web 完成/撤销为每份任务、动作、备注和证据生成输入指纹绑定的 `operation_id`，同任务写入与脚本运行互斥；按钮、记录面板和局部反馈表面呈现 pending、可聚焦错误、成功回执与晚响应同步状态。备注与证据分别以最多 500 个 Unicode 字符的精确值进入指纹和事件，超长输入明确拒绝而不截断。服务端以单调 `revision`、跨进程本地文件锁和 Git ignored 的独立操作账本先记录 pending，再原子替换进度、带同版 revision 的镜像、动作日志和反馈，最后标记 committed；响应必须携带与本次操作一致且仍存在于当前动作日志的持久化 event，前端完整校验 `done / done_at`、快照、event 和消息后一次提交状态。可捕获异常恢复精确写前内容；进程中断恢复前先验证 WAL 的输入指纹、基准/目标状态、revision 与 event，损坏记录零写入拒绝，合法 pending 才前滚。读档作为新 revision，不回退或删除幂等账本；若恢复的历史已移除某个 event，对应旧 ID 继续占用但重放明确失败，不从账本复活事件。
- 原因：在不引入数据库的当前本地单课程架构内，使用户看到的完成状态、保存证据和 ActionEvent 尽量形成一个可恢复事实，同时遵守 Depth Button 的物理状态和移动 44px 触控关系；Figma 示例中的 Attempt、XP 和 Mastery 仍不属于当前事实。
- 后果：同一输入在超时、网络中断或成功响应无法核对时复用 operation ID，避免重复写事件；明确 4xx 拒绝后则生成新 ID，避免永久无效 ID 形成重试死循环。修改输入也会获得新 operation ID。操作账本不是学习历史或存档内容，不进入 Git；`events.jsonl` 仍是用户可见动作真源。该机制不是跨设备数据库事务，未来迁入数据库或实现正式 Attempt 时应重新评估 WAL 与 revision 边界。
